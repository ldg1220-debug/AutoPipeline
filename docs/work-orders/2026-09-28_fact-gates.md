## 8. ★★ keyword 정정(`d6f6daa`)의 부작용 — 동의하는 지적

```
① 원본 키워드 보존

   중복 발행 체크·키워드 소진 기록은 원본으로 해야 다음 실행에서 또 뽑히지 않습니다.

② 이미 같은 지역·같은 일수 글이 있으면 발행하지 말 것
   "세부 5박 7일" → "세부 2박3일" 로 줄였는데 이미 "세부 2박3일" 글이 있으면
   같은 검색어를 두 글이 나눠 먹습니다. → 스킵 + 기록
```

### 휴양지는 이제 3일로 줄일 필요가 없습니다

트레쥴이 휴양형을 7일까지 받습니다(오늘 확인).

```
세부 days=5  →  요청은 받음 (400 아님)
세부 days=7  →  요청은 받음
```

**휴양형 키워드는 3으로 클램프하지 말고 원래 일수로 요청하세요.**
다만 지금은 트레쥴 쪽 후보가 모자라 **422** 입니다(세부 d5 9/10곳, d7 13/14곳 — 짝 지시서).
**422 이면 일수를 줄여 쓰지 말고 스킵하세요.** 트레쥴이 고쳐지면 그대로 살아납니다.

## 처리 결과 (2026-09-28)

- §2(최우선): `findDayTotal()` 신규(`day` 필드 직접 매칭, 배열/객체 두 형태 모두
  지원) — `monetizer.js`·`write-kin-answer.js` 양쪽의 `dayTotals[String(day)]`
  배열 인덱스 오독 수정. 실측 데이터로 재현 테스트 완료(1일차 7.2·2일차
  17.6·3일차 0으로 정확히 매칭).
- 게이트③: `sanitizeOutlineForbidden(outline)` 신규 — 숙소·가격대·예산·비용
  산정·경비 섹션을 트레쥴 데이터 유무와 무관하게 아웃라인 단계에서 제거.
- 게이트④: `stripUnsourcedMoney()` 신규 — 금액 패턴(원/₱/$) 포함 문장 삭제.
- 게이트⑤: `stripFirstPersonExperienceClaims()` 신규 — 1인칭 체험 표현 포함
  문장 삭제.
- 게이트①: `stripExceedingDayMentions()` 신규 — "N일차"·"Day N"·한글 서수
  ("넷째 날")가 `tripData.days`를 넘는 문장 삭제.
- 게이트②(일자별 분할 생성): **착수 안 함** — "규모: 중"으로 표시된 대로 Pass3
  본문 생성 자체를 일자 단위로 재설계해야 해서 이번 범위에서 리스크 대비
  효과가 낮다고 판단. 대신 게이트①(사후 문장 삭제)이 같은 증상(다른 날 언급)
  일부를 완화한다 — 근본 해결은 아니므로 재발 시 후속 작업으로.
- 게이트⑥(숫자 대조): 착수 안 함 — §2 버그를 고치면 세 갈래 거리 표기 문제
  자체가 사라지므로 우선순위를 낮췄고, 평점·리뷰수 사후 대조는 스팟명 매칭이
  필요해 이번 범위를 넘는 별도 작업으로 판단.
- §8-①②: `original_keyword` 보존(`run-blog-pipeline.js`, Part 1.7에서
  keyword 정정 시), 정정된 키워드가 이미 발행된 포스트와 겹치면 스킵.
  `blog_publisher.js`의 `savePublishResult()`가 `original_keyword`로
  `keywords` 테이블의 'used' 마킹을 하도록 분리(정정된 값으로 마킹하면
  원본 keywords 행이 안 잡혀 다음 실행에서 재선정될 위험이 있었음).
- §8(휴양형 클램프 해제 + 422 스킵): `tradule_source.js`의 day-retry 루프를
  `style==='resort'`일 때는 건너뛰도록 정정(원래 요청한 일수만 시도, 부족하면
  스킵) — 트레쥴이 5~7일 요청 자체는 받아주므로(400 아님) 3일로 줄여 쓰지
  않는다.
- §7(관련 포스트 제목 동기화): 착수 안 함 — DB 스키마·발행 파이프라인 구조를
  더 조사해야 안전하게 고칠 수 있어 이번 범위에서는 보류.
